# Data Model: Django 5.2 LTS Upgrade and Dependency Refresh

**Plan**: [plan.md](plan.md) | **Research**: [research.md](research.md)

This feature adds no business entity. It changes four things that hold state or versions: the
runtime dependency list, the migration history, the service data volumes and the seed dataset
that refills the server.

## 1. Runtime dependency list (`requirements.txt`, PR 1)

The only runtime dependency list. It is consumed by the Dockerfile
(`pip install -r /app/requirements.txt`) and by local setup (README).

| Part | Contents | Rule |
|---|---|---|
| Header comment | What the file is for, who reads it, how to regenerate the transitive group | It names the image build **and** local development. |
| Direct group | Django, djangorestframework, drf-spectacular, psycopg2-binary, python-dotenv, gunicorn, whitenoise, pgvector, onnxruntime, numpy, sentencepiece, huggingface-hub, celery[redis], kombu, redis | Each is something the code imports or the image runs (R2). |
| Transitive group | Everything the direct group pulls in on Linux, from `pip freeze` in the built image | It contains no Windows-only packages such as `colorama`, and no orphans such as `pytz`. |

**Validation rules**:
- Every line is `name==version`; extras are allowed, as in `celery[redis]`.
- No package appears twice.
- `pip install -r requirements.txt` succeeds for CPython 3.12 on `manylinux` `x86_64` and
  `aarch64` with `--only-binary=:all:`.
- `pip check` inside the image reports no broken requirements.
- Every pin is the package's latest release, except where research R1 records why it is lower.
  Today those exceptions are Django (5.2 LTS line) and redis (kombu caps it below 6.5).

**State change**: there are two lists today, the root one (commented) and
`library/requirements.txt` (a copy with no comments). After PR 1 there is only the root one
(FR-015).

## 2. Migration history (PR 1)

| App | New migration | Operation | SQL effect | Rollback to the 4.1 image |
|---|---|---|---|---|
| `authentication` | `0003_alter_customuser_role` | `AlterField role: IntegerField(choices=[(0, 'visitor'), (1, 'librarian')], default=0)` | None (choices are state only) | Safe |
| `order` | `0003_alter_order_id` | `AlterField id: BigAutoField` | `id` and its sequence become `bigint`. No foreign key points to `order.id`. | Safe, because the 4.1 code also models `id` as `BigAutoField` through `DEFAULT_AUTO_FIELD` |

**Rules**:
- Both are generated by `makemigrations` on Django 5.2.18 and committed unedited.
- The `0001`/`0002` migrations stay unchanged.
- Afterwards, `makemigrations --check --dry-run` reports no changes, enforced by a test.

## 3. Service data volumes (PR 3)

| Service | Before | After | Mount path |
|---|---|---|---|
| `db` | `pgvector/pgvector:0.8.2-pg15`, volume `pgdata` | `pgvector/pgvector:0.8.7-pg18`, volume **`pgdata18`** | `/var/lib/postgresql/data` → **`/var/lib/postgresql`** (data in `18/docker`) |
| `redis` | `redis:7.4-alpine`, volume `redisdata` | `redis:8.10.2-alpine`, volume **`redisdata8`** | `/data` (unchanged) |

The names and paths are identical in `docker-compose.yml` and `docker-compose-dev.yml`.

**Lifecycle on the server**: the old volumes go from active, to orphaned but kept for rollback,
to deleted. Each step:

```text
pgdata, redisdata (active)
   │  merge PR 3 → webhook redeploy
   ▼
pgdata18, redisdata8 (new, empty → migrated → seeded)      pgdata, redisdata (orphaned, kept)
   │  SC-009 verified on the Pi                                  │  revert PR 3 = back to these
   ▼                                                             ▼
pgdata18, redisdata8 (active)                              deleted by the operator (R14 step 6)
```

Once the old volumes are deleted, rolling back PR 3 needs another reset and reseed (spec edge
case "Rolling back").

## 4. Seed dataset (PR 3 refill)

`library/seed_db.py` creates the demo users (`librarian@`, `reader@`, `alice@` and
`bob@library.com`), authors, books and orders. It does nothing once any user exists.

**Rules for the reset**:
- **Precondition**: the server's current users are exactly the four seeded e-mail addresses, and
  the author, book and order counts equal those of a freshly seeded development stack. Otherwise
  the reset is not allowed.
- **Postcondition (SC-009)**:
  - The counts match the fresh development stack again.
  - Every book has a `BookEmbedding` tagged with the current model.
  - The four demo passwords have been replaced.
- The reference counts come from running the same seed script on a fresh development stack
  ([quickstart.md](quickstart.md) §4). They are not hard-coded, so later changes to the seed
  script keep the check valid.

## 5. Deprecation list (`deprecations.md`, PR 1)

There is one row per distinct warning still raised after PR 1. Every row is third-party, because
project-code warnings are fixed (FR-010).

| Field | Meaning |
|---|---|
| Warning | Category and message, e.g. `RemovedInDjango60Warning: …` |
| Raised by | Package and module that triggers it |
| Removed in | Release that removes the deprecated feature |
| Expected resolution | Usually "fixed by upgrading <package> to <version>", or a tracking issue link |
